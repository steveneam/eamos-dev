## Executive verdict

Eamos is well tested but not yet lean. Its test and lint baselines are unusually
strong for a repo of this age, but they currently protect a large, duplicated
shape rather than forcing that shape to simplify. The most important result of
this audit is that file length is not the first release risk:

1. **P0 — object authorization is missing on mounted legacy run/review routes.**
   A locally authenticated user is checked for a valid token, but run ownership
   is not checked before read, review, report mutation, chat, approval, drop, or
   PDF access.
2. **P1 — the active search UI and backend disagree on authentication.** The
   browser sends a Supabase access token; `/api/v1/search` accepts only the
   legacy local Eamos token.
3. **P1 — repo and live Supabase schema have drifted.** The backend queries
   `public.user_library` first, but the live project does not have the repo's
   `20260614195800_user_library_document.sql` migration.
4. **P1 — runtime dependency advisories are blocked by current version caps.**
   The highest exposure is `pypdf`, because Eamos processes user uploads.
5. **P1 — the Render→VPS migration is well planned but Eamos has not completed
   Phase 1.** Runtime ownership, one small-asset dry run, Render/source manifest
   comparison, Supabase egress confirmation, and a container/deploy contract
   are still open.
6. **P2 — structure debt is real.** The active app has 31 source files over
   1,000 lines; including the frozen Vite tree raises that to 34. Thalon has no
   source file over 1,000 lines, and Swordfish has none.

The recommended order is therefore **authorization → auth/schema drift →
vulnerable dependencies and CI → frozen frontend/dead code → package folds →
Render cutover readiness**. Splitting large files before closing the access and
schema gaps would optimize the wrong risk first.

  and `guard`.
- Focused packages for contracts, database, engine, and platform concerns.
- Feature-local tests and production modules that generally remain below 500

- Task-shaped infrastructure directories such as `provisioning/dokploy`,

## P0 — security boundary before refactoring

### Mounted run routes authenticate but do not authorize the object

`app/backend/app/core/deps.py` contains an explicit TODO for patient/run
ownership. The routes in `app/backend/app/api/routes/runs.py` and
`reviews.py` accept any valid legacy local user and then call services with only
`run_id`; they do not pass or compare the authenticated user ID. The affected
surface includes:

- `GET /api/v1/runs/{run_id}`;
- review and report-payload mutation;
- run chat and chat streaming;
- approve and drop;
- inline PDF retrieval.

These routers are mounted in ordinary `create_app()` construction. Local user
registration is also mounted, so “the UI no longer links to `/runs`” is not an
authorization control. Run IDs are high-entropy, which reduces opportunistic
guessing, but unguessability is not ownership enforcement.

Required correction:

1. standardize these routes on `AuthenticatedPrincipal`;
2. persist/resolve `owner_user_id` for every run/report;
3. require owner equality (or an explicit server-side role policy) inside the
   repository/service boundary, not only in the route;
4. return 404 or 403 consistently without leaking whether another user's object
   exists;
5. add two-user negative tests for every read and mutation class;
6. remove the duplicate `/api/v1/runs/{run_id}/review` registration while the
   route surface is being normalized.

This is a prelaunch gate even though `/runs` is a frozen product surface.

## P1 — functional, schema, dependency, and deployment blockers

### 1. Supabase/local auth split breaks active search

`app/web/lib/search/api.ts` obtains a Supabase session token and sends it to the
Next proxy. `app/backend/app/api/routes/search.py` uses
`require_authenticated_user`, which validates only the legacy local Eamos JWT.
Other newer routes correctly use `require_authenticated_principal`, which can
validate both local and Supabase principals.

Required correction: move search to `AuthenticatedPrincipal`, keep the existing
owner-scoped `SearchAccessContext`, and add a real Supabase-JWT route test plus a
local-token compatibility test. Review reports/runs separately because changing
their dependency without ownership enforcement would widen access before it is
safe.

### 2. Live Supabase is healthy and RLS-clean, but one required table is absent

Read-only live checks on project `cpdjxsgasaesysvxkpmi` found:

- project `eamos-dev` is `ACTIVE_HEALTHY`, PostgreSQL 17, Sydney region;
- Supabase security advisor returned no findings;
- RLS is enabled on the reviewed public, private, and storage tables;
- performance advisor findings were informational: 18 currently unused indexes
  and an Auth connection allocation expressed as a fixed count.

The live migration ledger and table inventory do **not** contain the repo's
`20260614195800_user_library_document.sql` / `public.user_library`. Yet
`SupabaseVariantLibraryRepo.get_document()` always queries that table first.
`VariantLibraryService.get_library()` converts the resulting repo error to 503
instead of falling back to normalized `collection` / `saved_variant` tables.

There is also migration-ledger naming drift:

- local `20260606134652_variant_library_persistence.sql` corresponds to a
  differently versioned remote migration;
- local `20260606051914_variant_library_folder_fk_index.sql` also has a
  differently versioned remote entry;
- `docs/db/supabase-inventory.md` is intentionally historical but now too stale
  to act as an operational inventory.

Do not blindly push migrations. First perform a signed-in library smoke against
the live backend, reconcile local-to-remote migration identity, review the SQL,
then apply only the missing migration with rollback/verification steps. The 18
unused indexes should be observed after real traffic; “unused today” is not
enough evidence to delete them.

### 3. Runtime dependency advisories need dedicated upgrade PRs

Current scans on 2026-07-15:

| Surface | Result | Important exposure |
| --- | --- | --- |
| `app/web` production deps | 14 moderate | DOMPurify advisories; PostCSS XSS; OpenTelemetry/PostHog memory growth; protobufjs |
| frozen `app/frontend` production deps | 3 low, 1 high | Vite Windows path/NTLM issues; React Router CSRF; esbuild dev-server file read |
| backend requirements + dev requirements | 45 advisories in 7 packages | `pypdf`, LangChain family, `cryptography`, pytest |

Backend caps currently prevent patched versions: LangChain is capped below 0.4,
`pypdf` below 6, `cryptography` below 46, and pytest below 9. `pypdf==5.9.0`
has the largest advisory set and parses user-supplied documents, so it is the
first upgrade lane. Do not use `npm audit fix --force`; its proposed dependency
movement is not a reviewed migration plan.

Deptry also exposed packaging drift: `pyproject.toml` declares no project
dependencies while runtime dependencies live only in requirements files. That
makes standard metadata tooling report false positives and obscures direct
dependencies such as `langchain_core`, `starlette`, and `botocore`. Optional PDF
engines (`pdfplumber`, `fitz`) and `psutil` need explicit extras or documented
operator installation instead of implicit imports.

### 4. CI proves tests, not deployability or security

Green gates:

- active web ESLint and TypeScript;
- active Next production build;
- frozen Vite ESLint and 139/139 Vitest tests;
- backend Ruff and Black;
- backend pytest: 1,619 passed, 20 skipped;
- backend boundary tests.

But `.github/workflows/ci.yml` does not run either frontend production build,
Ruff, Black, dependency audits, or secret scanning. The omitted build matters:
the active Next build passes, while the frozen Vite build currently fails from
both `VariantReportProfile.section_signals` drift and incompatible Vite 8 /
Vitest 3 plugin types.

Gitleaks scanned 532 commits / about 121 MB and reported seven generic-key
candidates. Manual redacted review found code identifiers, a ClinVar accession,
a localStorage key, URLs/status text, and one intentionally public Supabase
publishable key from a historical demo branch; no private credential was
confirmed. Add a reviewed baseline/config and fail CI on new findings so the
current false positives do not make the scanner unusable.

### 5. Render→VPS Phase 1 is not yet complete

Swordfish has completed Phase 0: `/srv/project1/assets`, restic exception and
restore proof, the `asset-manifest` harness, and a deploy-only Dokploy tenant
credential. Eamos still owns these zero-spend Phase 1 items:

1. confirm the container uid/gid that writes the bind mount;
2. choose the Dokploy-app-shell or Swordfish-CI-hands dry-run route;
3. pull and checksum one small asset, suggested ClinGen at about 528 MB;
4. produce source-bucket and live-Render-disk manifests, upload anything that
   exists only on Render, and review the diff;
5. confirm the Supabase plan covers roughly 41 GB of later egress;
6. supply a container/deploy contract for Dokploy.

`render.yaml` currently declares only an environment-variable group with seven
Render disk paths. It does not declare the backend service image/build, health
check, command, resource/mount contract, or the target `/srv/project1/assets`
mapping. Treat it as a path fragment, not as a reproducible deployment spec.

Hard boundaries remain: Supabase Postgres/Auth/Storage stay managed; the VPS
disk is a cache; no bulk seed occurs before Steven's resize approval; Render is
cancelled only after checksum proof, nothing-only-on-Render proof, and a clean
parallel soak.

- active web typecheck/lint/build;

## Controls that are already good

- 1,619 backend tests passed; only 20 intentional skips.
- Active web lint, typecheck, and production build pass.
- Ruff and Black are clean.
- Supabase security advisor is clean and reviewed tables have RLS enabled.
- Stripe webhook verification checks timestamp tolerance, signs the raw body,
  and uses constant-time `hmac.compare_digest`.
- Materialization admin endpoints require authentication, a disabled-by-default
  feature flag, a hashed admin token, and a narrow rate limit.
- Upload endpoints validate size and PDF signature; AI/provider calls have
  bounded timeouts.
- Rate limiting is disabled from untrusted proxy headers by default.

The remaining caveat is that rate limiting is in-memory and per process. It is a
useful single-instance guard, not a durable billing/security quota for a
multi-replica Dokploy deployment. Paid/AI budgets should move to a shared store
before horizontal scaling.
