## Verdict: **SYSTEMIC**
The OOM-class pattern (heavy compute / large in-RAM buffers / unbounded IO synchronously in the request path) appears across at least 8 independent subsystems — protein annotation, gene-viewer, lookup orchestration, coordinate index, predictors (ClinVar XML), clinical-tables/PubMed, cache repos, batch/VCF ingest, and the frontend viewer — not just the one protein path. Confirmed request-path-reachable (reachable:yes) instances of the exact same class include: the SAME hmmscan call reachable from 3 routes (protein-1, viewer-1, lookup-orchestration-1); gzip-bomb + whole-file VCF materialization on an UNAUTHENTICATED route (core-routes-misc-services-2, CRITICAL); the entire compact coordinate index loaded into RAM in-request and reachable from unauthenticated /health (coordinates-index-1); two independent full-DOM ClinVar XML parses per lookup (predictors-1, predictors-2); per-request full-table select*+fetchall checksums over the whole PubMed and ClinGen corpora (clinical-tables-pubmed-1/2); a table-wide DELETE on every variant-cache READ (cache-repos-2); two health endpoints that .all() an ungated full-table select (source-cache-repo, materialization-clis-1); and unvirtualized per-base DOM rendering in the frontend (frontend-report-viewer-1/4). Critically, gene_context_snapshot.build() — which triggers the protein annotation — runs UNCONDITIONALLY on every lookup even on a 100% variant-cache hit (lookup-orchestration-3), so the heavy path is not gated behind cache misses. The recurrence of the identical anti-pattern in subsystems built by different code paths, several reachable without authentication, is the signature of a systemic design assumption ('assets fit in RAM / compute can run in-request') rather than isolated bugs. It is NOT merely 'localized' because it is not a handful of hot files; the same three or four root patterns repeat almost everywhere external data or large assets are touched. The user's suspicion of systemic leaks is correct.

## Executive summary
The production OOM (synchronous HMMER hmmscan on a 5,202-aa protein inside a 2GB Render instance) was not a one-off. It is the most acute instance of a repo-wide architectural pattern: heavy compute, whole-asset reads, and unbounded result-set materialization executed synchronously on the FastAPI request thread. The audit confirms 60 findings (5 critical/high enough to OOM or crash; the rest degrade latency, leak memory, or saturate the worker pool). The same hmmscan call is reachable from THREE request paths — POST /viewer, POST /protein/annotate, and (most dangerously) every POST /lookup/summary + /lookup/sections call via gene_context_snapshot.build() which is NOT cached and runs even on a full variant-cache hit. Beyond protein: gzip-bomb VCF upload with no size cap on an unauthenticated route, a whole-table-into-RAM compact-coordinate-index load reachable from unauthenticated /health, full-DOM ClinVar XML parsed twice per lookup, per-request full-table checksums over the PubMed/ClinGen corpora, a DELETE-on-every-read in the variant cache hot path, and full-table scans behind two health endpoints. The frontend mirrors the backend: a full-locus viewer and AlphaMissense heatmap render one DOM node per base/residue with no virtualization (browser-crash class on CFTR/ABCA4/USH2A). Codex's residue-cap fix (a9de024) stopped USH2A specifically, but the cap sits one residue above the next gene, is request-time not architectural, and disables itself at 0 — it is a patch, not a fix. The correct remedy is architectural: move heavy compute off the request path (precompute/cache-warm/background), make web tiers serve cache-or-fail-closed, stream instead of whole-file read, bound every externally-driven result set, and right-size the instance.

## Systemic patterns

### Heavy compute (subprocess + external tools) executed synchronously on the FastAPI request thread, gated only by a request-time numeric cap and a wall-clock time
*Files:* app/backend/app/services/protein_annotation.py, app/backend/app/services/gene_viewer.py, app/backend/app/services/lookup_service.py, app/backend/app/api/routes/protein_annotation.py, app/backend/app/services/crispr_design.py, app/backend/app/services/workflow.py, app/backend/app/services/search_input_resolver.py
*Fix:* Establish a hard architectural rule: web tiers serve cache-or-fail-closed (allow_run=False) and never spawn heavy subprocesses or chain blocking upstream HTTP in-request. Run hmmscan/annotation/heavy resolution as offline cache-warmers or background jobs that only populate the cache. Where in-request execution is unavoidable short-term, add (a) a process-wide concurrency semaphore (<=1-2), (b) RLIMIT_AS on child processes via preexec_fn, (c) measured-RSS-based caps (not round numbers), and (d) per-request external-call deadlines. Treat cap<=0 as 'safe default', never 'unbounded'.

### Whole-asset / whole-file / whole-table read fully into RAM instead of streaming or keyed lookup — gzip.decompress + splitlines, read_text().splitlines(), read_b
*Files:* app/backend/app/services/vcf_ingest.py, app/backend/app/services/compact_coordinate_index.py, app/backend/app/services/eamos_coordinate_resolver.py, app/backend/app/services/clinical_consensus.py, app/backend/app/services/functional_evidence.py, app/backend/app/services/pubmed_local.py, app/backend/app/services/clingen_local.py, app/backend/app/services/protein_annotation.py, app/backend/app/services/repeatmasker_local.py, app/backend/app/services/transcript_model.py
*Fix:* Stream everything: incremental gzip with a decompressed-bytes ceiling; line-by-line iteration not splitlines(); ET.iterparse(stream)+elem.clear() not fromstring; chunked hashing not read_bytes(); tabix/bigBed/sqlite byte-range or keyed lookups instead of in-RAM interval tables and JSONL tuples. Disallow raw-GFF and raw-flatfile linear scans on the request path entirely (flip EamosLocalCoordinateResolver GFF-path defaults to None; require a prebuilt index). Move full-table checksums to startup/materialization (manifest checksum), never per-request.

### Unbounded externally-driven result sets and HTTP response bodies materialized with no LIMIT, no max-size, and no window-width cap — full ClinVar/Ensembl/VV/VEP 
*Files:* app/backend/app/repos/source_cache_repo.py, app/backend/app/services/clinical_consensus.py, app/backend/app/services/gene_viewer.py, app/backend/app/services/indexed_sources.py, app/backend/app/services/ai_gateway/retrieval.py, app/backend/app/services/clingen_local.py, app/backend/app/services/search_candidate_resolver.py, app/backend/app/services/variant_library.py
*Fix:* Cap every externally- or caller-driven result set: max Content-Length on upstream fetches (stream + abort), SQL GROUP BY aggregation instead of .all() on health/summary endpoints, LIMIT + numpy dot-products (not per-element Python cosine) for embedding retrieval, max window-width/row-count on tabix/bigWig queries, FTS5/indexed-term paths instead of lower(raw_json) LIKE, and hard pagination on list_variants. Bound inbound request bodies with pydantic max_length + an ASGI/proxy body-size limit.

### Process-global / in-process state that grows without bound or rebuilds heavy assets per request — unbounded _uploads/_jobs/_buckets/_fixture_cache dicts, never-
*Files:* app/backend/app/services/batch.py, app/backend/app/core/rate_limit.py, app/backend/app/services/gene_viewer.py, app/backend/app/services/sequence_context.py, app/backend/app/services/crispr_ssodn.py, app/backend/app/services/alphamissense_local.py, app/backend/app/services/compact_coordinate_index.py, app/backend/app/tools/base.py
*Fix:* Bound and right-size in-process state: LRU/TTL on _uploads/_jobs, delete empty rate-limit buckets after prune (move to Redis for multi-instance), bound _fixture_cache. Open expensive read-only assets (hg38.2bit, AlphaMissense tabix, compact index) ONCE per process/worker behind a guarded lazy singleton and reuse the handle across requests and exons, instead of resolve+open+parse+close per call. Cache parsed fixtures process-lifetime.

### Cache-read amplification and unconditional rebuilds defeating the caching layer — DELETE-on-read in the variant cache, gene_context_snapshot rebuilt on full cac
*Files:* app/backend/app/repos/variant_cache_repo.py, app/backend/app/services/lookup_service.py, app/backend/app/api/routes/lookup.py, app/backend/app/repos/variant_library_repo.py, app/backend/app/services/pubmed_local.py, app/backend/app/services/run_chat.py
*Fix:* Make reads pure reads (no DELETE), compute the full LookupResponse once and serve summary + every lazy section from one cached assembly keyed by gene:cdna, cache the gene_context_snapshot, batch N+1 loops into single bulk INSERT...ON CONFLICT / IN-list queries, and cache/persist the run-chat vector index by run_id+content-hash instead of re-embedding every turn.

### Unvirtualized per-element DOM rendering and O(n^2) per-render scans in the frontend viewer — one span per base, one rect+title per residue, full window-string r
*Files:* app/web/components/workbench/viewer/FullLocusViewer.tsx, app/web/components/report/ReportGeneViewer.tsx, app/web/components/workbench/viewer/CodonDetail.tsx, app/web/components/workbench/viewer/SequenceViewerV2.tsx
*Fix:* Virtualize large lists, cap full_gene render to a bp budget with a fallback, bin/canvas the heatmap, and hoist per-render scans into useMemo'd index Maps/Sets keyed on [flat, query]; wrap onRestrictionSelect in useCallback so blocksEqual holds during selection drags.

## Top risks (ranked)

### [CRITICAL] gzip-bomb + whole-file VCF materialization on an unauthenticated, size-unlimited upload route
- **Where:** `app/backend/app/api/routes/batch.py:17-29 + app/backend/app/services/vcf_ingest.py:76-85`
- **Why:** POST batch upload does await file.read() with NO max_upload_mb check, NO auth (no Depends), NO rate limit (verified vs intake.py/paper_variants.py which DO guard). _decode_payload then gzip.decompress()es the full body with no decompressed-size cap; VCF text compresses >1000:1, so a <20MB body expands to multiple GB in RAM, then splitlines() materializes the whole file plus a fanned-out variant list. Single unauthenticated request can OOM the 2GB instance — worse than the original protein OOM because it needs no warm asset and no login.
- **Fix:** Add Depends(require_authenticated_principal) + enforce_rate_limit; reject on Content-Length before reading; replace gzip.decompress with a streaming GzipFile that aborts past a decompressed-bytes ceiling; iterate lines from the stream and cap parsed-variant count (mirror the BatchCreateRequest 5000 cap onto the upload path).

### [CRITICAL/HIGH] Synchronous hmmscan reachable from 3 request paths incl. EVERY lookup (the production OOM class)
- **Where:** `app/backend/app/services/protein_annotation.py:227-253,576-612 + gene_viewer.py:1450-1462 + lookup_service.py:1038-1048`
- **Why:** LocalHmmerRunner.run() spawns hmmscan against full Pfam with capture_output buffering, on the sync request thread. Reached by POST /protein/annotate, POST /viewer, AND lookup_service.gene_context_snapshot.build() which runs on every /lookup/summary + /lookup/sections call. The only guard is a request-time residue cap (default 5000) that sits one residue below USH2A (5202), is bypassable at 0 (protein-5), and is a coding-residue count not a measured RSS bound. No concurrency semaphore: parallel large-protein requests sum past 2GB. This is the exact incident, still architecturally live for any <=5000aa protein.
- **Fix:** Move hmmscan off the request path entirely: cache-warm/background job; have /viewer, /protein/annotate and lookup serve allow_run=False (cache-or-fail-closed). Short-term: process-wide semaphore (<=1-2), RLIMIT_AS via preexec_fn, treat cap<=0 as safe-default not unbounded.

### [HIGH] gene_context_snapshot (and its protein annotation) rebuilt every lookup even on a full cache hit
- **Where:** `app/backend/app/services/lookup_service.py:1038-1048`
- **Why:** The variant_cache_repo short-circuit restores VEP/VV/gnomAD/SpliceAI/LitVar/PubMed, but the gene_context_snapshot block is unconditional and never stored in/read from the cache. So a 100%-cache-hit variant STILL pays the full gene-viewer source fetch + (cache-miss) hmmscan every time. This is why the OOM path is not gated behind a genuine cache miss — it is the amplifier that makes the protein finding production-critical rather than rare.
- **Fix:** Serialize and cache the gene_context_snapshot (incl. protein_domain_track) in variant_cache_repo alongside strict_genomic_cache, version-gated; rebuild only on refresh=True or missing/stale snapshot.

### [HIGH] Entire compact coordinate index loaded into RAM in-request, reachable from unauthenticated /health
- **Where:** `app/backend/app/services/compact_coordinate_index.py:231-309`
- **Why:** _load_index does rows = tuple(_iter_jsonl(path)) (every gzip-decompressed JSONL record) then builds multiple full dicts with each variant duplicated under two keys — no LIMIT, no streaming, no size guard. Reached on every cDNA lookup AND via the unauthenticated inspect_compact_coordinate_index health route. lru_cache(maxsize=16) keyed on (path, verify_checksum) can hold up to 16 full copies and TWO copies of the same artifact (checksum True vs False), with no lock against concurrent cache-miss rebuilds (thundering herd right after a materialize clears the cache).
- **Fix:** Load once at warmup behind a hard variant/transcript ceiling (fail to 'not ready' above it) or move to a keyed on-disk store (sqlite/LMDB) for single-row lookups; drop verify_checksum from the cache key, set maxsize=1-2, guard with a module lock; make /health read only metadata + stat(), never trigger a full load.

### [HIGH] ClinVar VCV XML parsed into a full in-memory DOM TWICE per lookup with no size cap
- **Where:** `app/backend/app/services/clinical_consensus.py:260-288 + functional_evidence.py:404-430`
- **Why:** Both clinical_consensus and functional_evidence independently do ET.fromstring(xml_text) then for elem in root.iter(): ''.join(elem.itertext()), each per /lookup. The VCV body is fetched with response.text and no max-size/Content-Length guard (predictors-3); a heavily-curated variant yields multi-MB XML, fully materialized into a tree TWICE in one request, doubling peak memory + CPU. Fires when use_real_apis is true — the posture prod was in when it OOM'd.
- **Fix:** Cap xml_text length (skip/warn above ~2-5MB), switch to ET.iterparse(stream) + elem.clear(), share ONE parsed pass between the two extractors, and ideally extract ACMG codes/PMIDs at cache-write time. Factor the two duplicate capped HTTP clients into one.

### [HIGH/MED] Per-request full-table logical checksum (select * + fetchall) over the entire PubMed and ClinGen corpora
- **Where:** `app/backend/app/services/pubmed_local.py:486-512,2610-2625 + clingen_local.py:196-216,732-745`
- **Why:** PubMedLocalStore.search_tool_result() unconditionally calls inspect(verify_checksum=True), which does select * ... fetchall() over pubmed_article (incl. full abstract_text + provenance blobs) and 4 other tables, then json.dumps each row — on EVERY lookup. ClinGenLocalStore.search_records defaults verify_checksum=True and ClingenTool does not override it, so the same full-corpus load happens per request. Memory scales with whole-corpus size on the hot path.
- **Fix:** Pass verify_checksum=False from the tools on the request path (PubmedTool, ClingenTool); reserve checksum verification for startup/health/materialization; never compute it via select*+fetchall — use the manifest checksum written at materialization.

### [MED (hot-path stability)] Table-wide DELETE executed on every variant-cache READ (SQLite write-lock contention on the hot path)
- **Where:** `app/backend/app/repos/variant_cache_repo.py:21-39`
- **Why:** get_fresh() runs delete(VariantCacheRecord).where(created_at < cutoff) BEFORE the read, in the same session_scope, turning every idempotent cache read into a write transaction. On the default SQLite DB, writes take a database-level lock; concurrent lookups serialize behind this DELETE and hit SQLITE_BUSY/'database is locked' under load — a stability cliff distinct from memory.
- **Fix:** Make get_fresh() a pure read (check created_at on the single fetched row); move expiry pruning to a periodic/CLI job or run it probabilistically (~1% of reads).

### [HIGH (browser)] Full-locus viewer + AlphaMissense heatmap render one DOM node per base/residue, no virtualization
- **Where:** `app/web/components/workbench/viewer/FullLocusViewer.tsx:80-117,170-222 + app/web/components/report/ReportGeneViewer.tsx:790-808`
- **Why:** FullLocusViewer maps all rows and one <span> per base for the entire locus; CFTR (~189kb)/ABCA4 (~128kb) produce thousands of rows / hundreds of thousands of spans. The AlphaMissense heatmap emits one <rect>+<title> per residue (~5,200 = ~10k nodes for USH2A). Both are the client-side mirror of the backend whole-asset-in-memory pattern and crash/hang the tab — the same large-gene blast radius (USH2A/CFTR/ABCA4) as the server OOM.
- **Fix:** Virtualize rows (react-window/react-virtual) and cap full_gene to a bp budget with a 'too large to render fully' fallback; bin/downsample the heatmap or paint to a single canvas with one hover readout instead of per-residue rect+title.

### [MED] Two health endpoints .all() an ungated full-table select over the unbounded source_cache table
- **Where:** `app/backend/app/repos/source_cache_repo.py:89-173`
- **Why:** health_summary() runs an ungated select(...).all(), materializing every row of source_cache (one row per (source, variant) ever cached — grows without bound) into a Python list and aggregating in Python. Reached from GET /health/provider-cache. On a warm prod cache this is a full-table scan + tens-to-hundreds-of-thousands-row list on a health route that monitoring/load-balancers may poll frequently.
- **Fix:** Do the aggregation in SQL (GROUP BY source, COUNT/conditional sums, MIN/MAX fetched_at); return one row per source. Never .all() an ungated select on a request handler.

### [MED] Unauthenticated /lookup/parse lets the caller force the heavy coordinate-resolution path
- **Where:** `app/backend/app/api/routes/lookup.py:92-104`
- **Why:** parse_lookup_input has NO auth dependency (contrast routes/search.py) and SearchInputParseRequest.resolve_coordinates is a client-settable bool flowing into EamosSearchInputResolver(resolve_coordinates=True). An anonymous client can repeatedly trigger coordinate resolution (and, with live mode, the 15s MANE/VV/rsID HTTP chain in search_input_resolver.py:309-441) per request. Rate limiting is per-IP with trusted forwarded-for headers, so it is spoof-bypassable.
- **Fix:** Require auth on /lookup/parse (match /search), derive resolve_coordinates server-side rather than trusting the client, add a dedicated low rate-limit scope, and do not trust forwarded-for for the IP key here.
