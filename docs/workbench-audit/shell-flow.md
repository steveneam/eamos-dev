## 1. Snapshot

The Workbench shell is a clinical sequence IDE: a shared `.nav-wrap` (logo · centred search · `ModePill`) → a slim `ContextStrip` (gene·variant left, segmented `ToolBar` right) → a `<WorkRail>` 2-column split (controls-left 336px ↔ canvas-right). The canvas vertically stacks `CanvasHeader` → `.viewer` → `.tool-panels`. The posture is genuinely strong — one shared rail across three surfaces, real collapse/drawer machinery, SSR-safe persistence, tokenised motion, and (newly) a real `--z-*` scale in `globals.css:190-197` that the rail already consumes. **Key freshness win: the `--z-*` scale both Task-A specs call "proposed" has SHIPPED** — `--z-rail/-nav/-scrim/-drawer/-popover/-pill/-modal` exist and `work-rail.css` + `InfoHint` + `workbench.css` nav already use the tokens.

The three biggest gaps vs the Benchling/Apple bar:

1. **The tool sits BELOW the viewer, not beside it (the core flow problem Task A exists to fix).** `WorkbenchShell.tsx:286` stacks `.tool-panels` under `.viewer` at full canvas width. On Primer/CRISPR the viewer keeps full height (`viewerCollapsed` returns true *only* for `align`, `tools.ts:50-51`), so the actual tool form is pushed far down the page — the eye lands on the sequence, then has to scroll to find the action. There is no left→center→right "context → see → act" reading order; it's "see → scroll → act." This is the single highest-leverage structural fix and the whole justification for the 3-col spec.

2. **Orphan + dead chrome competing for the same job.** Two collapse affordances exist in the rail: `WorkRail`'s own toggle/stub (live) AND a vestigial `SidePanel` collapse button (`SidePanel.tsx:735-747`) that is CSS-hidden (`workbench.css:1409-1411`), wired to a no-op (`onToggleCollapsed={() => {}}`, `WorkbenchShell.tsx:191`), with an unreachable `collapsed` stub branch (`SidePanel.tsx:749-752`, `collapsed` is hardcoded `false` at line 187). The parked `.ai-pill`/`.ai-panel` (bottom-RIGHT, `workbench.css:2896-2944`) is a CSS-only ghost with no JSX. The retired `.zoom-pill` preset CSS (`workbench.css:154-177`) is dead. Calm hierarchy requires removing these.

3. **The bottom-left corner is owned by the wrong thing, and the Scratchpad "Ask Eamos" tab is a parked feature spending a top-level tab slot.** Global `<CiteChip>` (`providers.tsx:39-41`) pins a report-centric Cite/Feedback dock at `bottom:16;left:16;z-index:900` (`CiteChip.tsx:271-276`) on *every* surface — it floats above even the `--z-modal:200` export modal (a latent bug; it predates the z-scale and never adopted it). Meanwhile there's no account affordance anywhere in the product shell, and the Scratchpad's third tab "Ask Eamos" (`SidePanel.tsx:309-317`) is a COMING-SOON placeholder occupying 1/3 of the tab strip. Task A's bottom-left cluster spec is the right corrective.

A cross-cutting freshness note that reshapes Task A: **`DESIGN.md:559-571` still documents the OLD workbench** — a `<TopNav/>`, a vertical `<ToolRail/>` icon rail, `<AskEamosPill/>` bottom-right, and `<WorkbenchShell/>` as `grid-template-columns: 64px 1fr 360px`. None of that matches the shipped tree (rolls its own `.nav-wrap`, horizontal `ToolBar` in ContextStrip, parked pill, 2-col WorkRail). The 3-col spec is in spirit a *return* to a 3-column shell — but with a **different column meaning** (controls | viewer | tool-rail) than DESIGN.md's (icon-rail | canvas | sidepanel). DESIGN.md must be reconciled when Task A lands (see §5).

## 3. Flow + eye-guidance

**Today's flow breaks the eye's path.** Reading order should be context → see → act, left to right. Instead: the eye enters at the centred nav search, drops to the ContextStrip identity, then to the `CanvasHeader` controls flush-RIGHT (`workbench.css:127` `justify-content:flex-end`), then the viewer fills the column, and **the active tool form is below the fold** (`.tool-panels` stacked under `.viewer`, `WorkbenchShell.tsx:286`). For Primer/CRISPR — where the form *is* the task — the user must scroll past a full-height sequence they didn't ask to act on. There is no single obvious primary action in view. This is the friction Task A's 3-col layout removes by promoting the tool into a right rail beside the viewer.

Concrete fixes for Apple-like seamlessness:

1. **Promote the tool beside the viewer (Task A core).** Adopt the §4 grid: `context (rail) | see (viewer) | act (tool)`. This makes the workflow the layout and puts the one primary action per tool (Primer's Generate, CRISPR's run, Align's Use-reference) in the same viewport as the sequence.
2. **One collapse vocabulary.** Remove the dead `SidePanel` collapse button (§2) so the rail has exactly one collapse affordance (WorkRail's toggle/stub). Two controls for the same job is the opposite of calm hierarchy.
3. **One Ask-Eamos home.** Collapse the Scratchpad "Ask" tab into the Task-A rail-foot launcher. Today there are *two* parked Ask entry points (Scratchpad tab + the CSS-ghost pill) and a third proposed in the foot — converge to one.
4. **One bottom-left cluster.** Move Cite/Feedback off the prime corner (Task A §5) and give that corner to account + Ask. A single utility cluster that rides the rail's collapse/drawer states (instead of a free-floating `z:900` dock that fights them) is the seamless posture.
5. **CanvasHeader controls left-align to the viewer they govern.** Flush-right (`:127`) puts the view controls maximally far from the rail and the gene name; under the 3-col grid they should sit at the top of the *center* (viewer) column, reading as "controls for this sequence."
6. **Glyph consistency on the rail toggles.** The WorkRail toggle (`WorkRail.tsx:186`) + FAB (`:215`) are the last hand-rolled `strokeWidth={2}` SVGs in the shell — route through the `Icon.tsx` 1.75 family so every shell glyph is one pen.

## 4. Task A — refined recommendation

Both specs are well-grounded and largely current. The one stale premise across them: they call the `--z-*` scale "proposed" — it has **shipped** (`globals.css:190-197`, consumed by `work-rail.css`). Update both to "adopt the existing scale" rather than "introduce" it; the `AuthMenu` dropdown should consume `--z-popover` (70) and the rail-foot popover-clipping caveat (3-col spec §6 / chrome spec §6) still stands because the rail is `overflow:hidden` (`work-rail.css:41`) + `position:sticky` (a new stacking context) — the foot's dropdown must portal out. The deeper reconciliation: **`DESIGN.md:567` already specs a 3-col `64px 1fr 360px` workbench** with a *vertical icon ToolRail* as col 1 — the 3-col spec must explicitly supersede that table (its columns are controls | viewer | tool-rail, not icon-rail | canvas | sidepanel), or the design system stays incoherent.

**Ecosystem fit.** The 3-col model is the single biggest flow upgrade and fits the shell cleanly *because* it reuses the existing grammar: Option C (grid-based canvas split + `.wr-section`/`WorkRailSection` chrome + the collapse helpers factored out of `WorkRail`) is the right call — it avoids the nested-sticky / inverted-semantics / `--rail-live-w` collision of a mirrored second `WorkRail`, keeps one stacking context, and reads as the same system as the left rail. The motion constraint (animate `grid-template-columns`, NOT the `.viewer` `max-height` pattern at `workbench.css:187`) is correctly identified. Container-relative breakpoints (`@container`) are essential — the panels' current breakpoints are *viewport*-based (e.g. CRISPR `max-width:560px`) and will NOT fire on a half-width rail inside a 1440px viewport; the subtlest risk, flagged correctly.
